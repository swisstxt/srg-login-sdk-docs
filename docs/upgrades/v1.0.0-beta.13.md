# Upgrade to v1.0.0-beta.13

> **Released**: May 2026 · **Codename**: "UserInfo"
> **Estimated effort**: ~15–30 min per app

This release introduces one major new feature — `srgLogin.getUserInfo()` for reading the End-User profile at any time — and two breaking refactors: profile claims move from `IdTokenClaims` to a dedicated `UserInfo` type, and `isAuthenticated()` is tightened to require a non-expired access token.

:::info Two breaking changes in the same milestone
LOGIN-1881 (UserInfo + claim split) was planned for beta.13 to align the SDK with the OIDC §3.1.3.7 / §5.3 separation between auth-proof claims and profile claims. LOGIN-1883 (strict `isAuthenticated()`) landed late in the cycle to fix a "flash of authenticated UI" risk raised after beta.12 was cut.

**RC.1 will not introduce any further breaking changes** unless a security issue forces it.
:::

## At a glance

| | |
|---|---|
| 🆕 New features | 1 (`srgLogin.getUserInfo()` + structured `UserInfo` type) |
| ⚠️ Breaking changes | 2 (profile claims moved from `IdTokenClaims` to `UserInfo`; `isAuthenticated()` strict semantics) |

## What's new

### 🆕 `srgLogin.getUserInfo(forceRefresh)` — End-User profile, any time

After login, BU apps frequently need to display the user's name, avatar, or email. Previously the only way to obtain these was to read `tokenSet.idTokenClaims` at `LoginState.Success` and cache it **inside the app** — which broke across process restarts and drifted when the IdP updated the profile.

The new `srgLogin.getUserInfo()` API gives a fast cached path and an opt-in refresh against the IdP:

<Tabs>
  <TabItem value="android" label="Android" default>

```kotlin
// Fast path — returns the snapshot persisted at the last login or refresh.
// Survives process restart. No network call. Typical for UI rendering.
when (val result = srgLogin.getUserInfo()) {
    is SdkResult.Success -> updateProfileHeader(result.data)
    is SdkResult.Failure -> handleError(result.error)
}

// Forced refresh — calls the OIDC /userinfo endpoint and replaces
// the cache. Useful when the user updates their profile in the IdP
// and you want the change reflected immediately.
val fresh = srgLogin.getUserInfo(forceRefresh = true)
```

  </TabItem>
  <TabItem value="ios" label="iOS">

```swift
// Fast path — returns the snapshot persisted at the last login or refresh.
// Survives process restart. No network call. Typical for UI rendering.
do {
    let info = try await srgLogin.getUserInfo(forceRefresh: false)
    updateProfileHeader(info)
} catch {
    handleError(error)
}

// Forced refresh — calls the OIDC /userinfo endpoint and replaces
// the cache. Useful when the user updates their profile in the IdP
// and you want the change reflected immediately.
let fresh = try await srgLogin.getUserInfo(forceRefresh: true)
```

  </TabItem>
</Tabs>

**Behaviour**:

| | `forceRefresh = false` (default) | `forceRefresh = true` |
|---|---|---|
| Network | none | `GET /userinfo` |
| Source | secure storage (cache) | IdP, then cache replaced |
| Access token | not used | obtained via `getAccessToken()` (transparent refresh on Expired) |
| Concurrency | parallel reads OK | concurrent calls serialised internally |
| `sub` mismatch check | N/A | OIDC §5.3.2 (response rejected on mismatch) |

**Security — sub mismatch protection (OIDC §5.3.2)**: the SDK verifies that the `sub` returned by `/userinfo` matches the access token's `sub`. On mismatch (mis-routed response, server bug, attack), the response is **discarded** and the failure carries `reason == "OIDC §5.3.2: userinfo sub mismatch"`. This exact string is a stable partial contract — pattern-matching on it is supported across SDK versions.

:::caution Empty cache ≠ unauthenticated
With `forceRefresh = false`, an empty cache returns `SdkResult.Failure(InvalidDataError("No cached UserInfo …"))`, **not** `NotAuthenticated`. An empty UserInfo cache also occurs for a valid session without the `openid` scope, or before the first login/refresh. Do **not** redirect to login on this error alone — call `getUserInfo(forceRefresh = true)` or check the session state instead.
:::

### 🆕 New claims exposed — `phone_number`, `phone_number_verified`

The `phone` scope claims are now first-class properties on `UserInfo`:

<Tabs>
  <TabItem value="android" label="Android" default>

```kotlin
val info = (srgLogin.getUserInfo() as? SdkResult.Success)?.data
info?.phoneNumber          // E.164 format, e.g. "+41791234567"
info?.phoneNumberVerified  // Boolean — IdP-verified
```

  </TabItem>
  <TabItem value="ios" label="iOS">

```swift
let info = try? await srgLogin.getUserInfo()
info?.phoneNumber          // E.164 format, e.g. "+41791234567"
info?.phoneNumberVerified  // Bool — IdP-verified
```

  </TabItem>
</Tabs>

These claims were silently dropped before — even when the IdP returned them in the ID Token. To receive them, request the `phone` scope at login:

<Tabs>
  <TabItem value="android" label="Android" default>

```kotlin
srgLogin.login(
    loginMethod = LoginMethod.Web,
    authContext = context,
    additionalScopes = listOf("profile", "email", "phone"),
).collect { /* ... */ }
```

  </TabItem>
  <TabItem value="ios" label="iOS">

```swift
for await state in srgLogin.login(
    loginMethod: .web,
    authContext: ctx,
    additionalScopes: ["profile", "email", "phone"]
) {
    // ...
}
```

  </TabItem>
</Tabs>

## ⚠️ Breaking changes

All breaking changes ship together in beta.13. After this migration, **RC.1 is functionally identical** to beta.13 — only the version number changes.

| # | Ticket | Before | After | Action |
|---|---|---|---|---|
| 1 | LOGIN-1881 | `tokenSet.idTokenClaims?.{name, email, picture, address, phoneNumber, …}` | `tokenSet.userInfo?.{name, email, picture, address, phoneNumber, …}` | Replace each profile read with `userInfo?` (mapping table below) |
| 2 | LOGIN-1881 | `idTokenClaims.defaultDisplayName()` | `userInfo.defaultDisplayName()` | Rename the call |
| 3 | LOGIN-1881 | `Address(...)` constructor and `address.copy(...)` were public | `Address` constructor + `copy()` are now `internal` | Obtain `Address` via `tokenSet.userInfo?.address` / `srgLogin.getUserInfo()`. Mock at the SDK boundary in tests rather than constructing `Address` directly. |
| 4 | LOGIN-1883 | `isAuthenticated()` returns `true` as soon as a refresh token is present (even with an expired access token) | `isAuthenticated()` returns `true` **only** if a non-expired access token is in storage | Add a silent `getAccessToken()` attempt before redirecting to login (example below) |

### Migration table for `IdTokenClaims` → `UserInfo`

| Before (beta.12) | After (beta.13) |
|---|---|
| `tokenSet.idTokenClaims?.name` | `tokenSet.userInfo?.name` |
| `tokenSet.idTokenClaims?.givenName` | `tokenSet.userInfo?.givenName` |
| `tokenSet.idTokenClaims?.familyName` | `tokenSet.userInfo?.familyName` |
| `tokenSet.idTokenClaims?.preferredUsername` | `tokenSet.userInfo?.preferredUsername` |
| `tokenSet.idTokenClaims?.picture` | `tokenSet.userInfo?.picture` |
| `tokenSet.idTokenClaims?.locale` | `tokenSet.userInfo?.locale` |
| `tokenSet.idTokenClaims?.updatedAt` | `tokenSet.userInfo?.updatedAt` |
| `tokenSet.idTokenClaims?.email` | `tokenSet.userInfo?.email` |
| `tokenSet.idTokenClaims?.emailVerified` | `tokenSet.userInfo?.emailVerified` |
| `tokenSet.idTokenClaims?.address` | `tokenSet.userInfo?.address` |
| `idTokenClaims.defaultDisplayName()` | `userInfo.defaultDisplayName()` |

**What stays on `IdTokenClaims`** (auth-proof claims, unchanged): `issuer`, `subject`, `audience`, `expiresAt`, `issuedAt`, `nonce`, `authorizedParty` (`azp`), `authTime`, `sessionId` (`sid`), `acr`, `amr`, `isExpired`, `isExpiredWithSkew(...)`, `sessionAge()`, `hasAudience(...)`.

**`isAuthenticated()` cold start — After** (attempt a silent refresh before redirecting to login):

<Tabs>
  <TabItem value="android" label="Android" default>

```kotlin
if (srgLogin.isAuthenticated()) {
    navigateToMainScreen()
} else {
    // Access token is missing or expired. Try a silent refresh once
    // before sending the user back to login:
    when (val result = srgLogin.getAccessToken()) {
        is SdkResult.Success -> navigateToMainScreen()
        is SdkResult.Failure -> navigateToLoginScreen()
    }
}
```

  </TabItem>
  <TabItem value="ios" label="iOS">

```swift
if try await srgLogin.isAuthenticated() {
    navigateToMainScreen()
} else {
    // Access token is missing or expired. Try a silent refresh once
    // before sending the user back to login:
    do {
        _ = try await srgLogin.getAccessToken()
        navigateToMainScreen()
    } catch {
        navigateToLoginScreen()
    }
}
```

  </TabItem>
</Tabs>

`getAccessToken()` performs the refresh transparently when the access token is expired and a refresh token is available. If the refresh succeeds the user sees no login prompt; if it fails (network, `invalid_grant`, …) the result is a clear failure and the caller can drive the UI accordingly.

Consumers that specifically want to know whether a silent refresh is possible (e.g. to display a "Restoring your session…" splash) can call `srgLogin.hasRefreshToken()` — its semantics are unchanged.

:::tip Migration tip
Search your codebase for these patterns to find every call site that needs updating:

```bash
git grep -nE 'idTokenClaims\?\.(name|givenName|familyName|preferredUsername|picture|locale|updatedAt|email|emailVerified|address|defaultDisplayName)'
git grep -nE 'Address\(|\.copy\('
git grep -nE 'isAuthenticated\('
```

Most apps have 1–3 call sites of `isAuthenticated()` (typically a single cold-start check in the app's root navigation graph or `ViewModel`).
:::

## Stability improvements *(no action required)*

- **Android HTTP engine: Ktor CIO → Ktor OkHttp** (LOGIN-1882). Resolves a known incompatibility ([KTOR-3540](https://youtrack.jetbrains.com/issue/KTOR-3540)) with Android's Network Security Configuration `<domain-config>` blocks — CIO did not call the hostname-aware `checkServerTrusted()` variant that `RootTrustManager` requires. HTTPS requests issued by the SDK now also appear in **Android Studio's Network Profiler**, and TLS goes through the platform-native (Conscrypt-backed) stack.
- **`UserInfo` cache self-heal on corruption** — `getUserInfo()` (cache path) now clears a corrupted entry automatically when it detects a `GeneralSecurityException` / `SerializationException` (e.g. after a schema drift between SDK versions), preventing repeated failures and Sentry error storms.
- **Logout cleanup expanded** — `performLocalLogout()` now also clears the anti-replay JWT-ID cache, the refresh-token rotation metadata, and the `UserInfo` profile cache (idempotent, best-effort). No more residual state surviving into the next session.

## Per-platform notes

### Android

#### Trust anchor on Android 7.0 / 7.1.0

Devices running Android 7.0 or 7.1.0 may hit a TLS error on the **INT** environment because the Let's Encrypt root certificate (ISRG Root X1) is absent from those devices' trust store, and the IdenTrust cross-sign that previously bridged this gap expired in September 2021.

If your app supports Android 7.x:

1. Bundle ISRG Root X1 as a raw resource: `res/raw/isrg_root_x1.pem` — download from [letsencrypt.org/certs/isrgrootx1.pem](https://letsencrypt.org/certs/isrgrootx1.pem)

2. Add a Network Security Config:

   ```xml
   <!-- res/xml/network_security_config.xml -->
   <?xml version="1.0" encoding="utf-8"?>
   <network-security-config>
       <base-config>
           <trust-anchors>
               <certificates src="system" />
               <certificates src="@raw/isrg_root_x1" />
           </trust-anchors>
       </base-config>
   </network-security-config>
   ```

3. Reference it in your `AndroidManifest.xml`:

   ```xml
   <application android:networkSecurityConfig="@xml/network_security_config">
   ```

:::tip `<domain-config>` is now also supported
Thanks to the LOGIN-1882 engine switch (Ktor OkHttp), the SDK is now compatible with the more scoped `<domain-config>` blocks. The `<base-config>` workaround documented above still works and remains a safe default — if your trust model favours per-domain scoping, you can switch, but it is not required.
:::

#### Min SDK

The SDK supports `minSdkVersion = 21` (Android 5.0). No change in this release.

### iOS

No specific iOS configuration is required for this release.

Thanks to the SKIE plugin, all Kotlin types — `LoginState`, `TokenSet`, `UserInfo`, `IdTokenClaims`, etc. — are available natively in Swift with idiomatic naming. Kotlin `Flow<T>` is exposed as Swift `AsyncSequence`, and Kotlin `suspend fun` is exposed as Swift `async fun`.

```swift
let states = srgLogin.login(loginMethod: .web, authContext: ctx)
for await state in states {
    if let success = state as? LoginStateSuccess {
        let info = success.tokenSet.userInfo
        // ...
    }
}
```

## Migration checklist

Use this checklist to track your migration:

- [ ] Bumped SDK dependency to `1.0.0-beta.13`
- [ ] Replaced every `idTokenClaims?.{name, email, picture, address, …}` profile read with `userInfo?…` (see the mapping table)
- [ ] Renamed `idTokenClaims.defaultDisplayName()` to `userInfo.defaultDisplayName()`
- [ ] Removed every direct `Address(...)` / `address.copy(...)` call — `Address` is now obtained via the SDK only
- [ ] Added a silent `getAccessToken()` attempt before redirecting to login when `isAuthenticated() == false`
- [ ] *(Optional)* Requested the `phone` scope at login if your app needs `phoneNumber` / `phoneNumberVerified`
- [ ] *(Android only)* Verified your existing Network Security Config still works; optionally switched from `<base-config>` to the more scoped `<domain-config>` if it suits your trust model
- [ ] If you display user info, considered using `srgLogin.getUserInfo()` (cached or `forceRefresh = true`) instead of caching `tokenSet.idTokenClaims` inside the app
- [ ] Smoke-tested login, token refresh, `getUserInfo()`, and logout end-to-end on Android and iOS
- [ ] Verified your CI still passes after the dependency bump and the migration
